## Blockers (must fix before tagging)

### B1 — The shipped CHANGELOG claims `/ws/agent` requires a local origin; the code deliberately no longer gates it at all
**`CHANGELOG.md:21`** — verified, with the predicates executed directly and raw upgrades measured against a live server.

The Security section reads: "**`/ws/terminal` and `/ws/agent` require a local origin (review B3).** They accepted unauthenticated cross-origin upgrades…". At HEAD, `MACHINE_SCOPE_SOCKETS = new Set(['/ws/terminal'])` (`src/ws-origin.ts:96`) and `src/ws-origin.test.ts:38` *asserts* `requiresLocalOrigin('/ws/agent') === false` — the ungating is pinned by test, so it is a decision, not an oversight (`0a3d170`: "I gated `/ws/agent` too, which broke programmatic agents"). Measured live: `Origin: https://evil.example` → `/ws/agent` **101**, `/ws/terminal` **403**, `/ws/browser` **101**. A foreign-origin socket received a broadcast payload carrying an absolute filesystem path.

The claim is wrong in three directions, not one:
1. `/ws/agent` is not gated at all.
2. `/ws/terminal` does not "require a local origin" either — an **absent** `Origin` header is admitted unconditionally (`src/ws-origin.ts:74`), and the server binds `0.0.0.0`. The code comment concedes this is "forgeable by anything on the LAN."
3. `isLoopbackOrigin` matches on **hostname only, any port**, so a third-party script on your own `http://localhost:3000` dev server passes.

`package.json`'s `files` includes `CHANGELOG.md`, so this ships in the tarball. The identical stale claim also sits at `reviews/1.12.9-tier1-v1.12.6-to-v1.12.8.md:7`, which now certifies a fix that was subsequently reverted. `CLAUDE.md` and `SKILL.md` are clean.

**Why this is a blocker and not a doc nit:** `src/ws-origin.ts:11-13`, written for this very release, says "**A false completeness claim in a security note propagates outside the repo.**" That is the shape B3/M1 was scored a blocker for, and this is the release that exists to satisfy the exit criterion "stop the code, the test name, the 403 body and the CHANGELOG from asserting a property they do not have." The CHANGELOG leg of that criterion is unmet.

**Fix — prose only. Do NOT re-gate `/ws/agent`.** Verification established that the ungating is correct on the merits: `jsonHeaders()` (`src/server.ts:941-947`) already sets `Access-Control-Allow-Origin: *` **and** `Access-Control-Allow-Private-Network: true` on the whole REST surface, so any page can already `POST /tree` and `/eval` cross-origin and poll `messageBuffer`. Gating the socket alone closes nothing and breaks non-browser agents. Rewrite the bullet to state what shipped:
- `/ws/terminal` admits a loopback **hostname** origin (any port), or an opaque/`file:` origin presenting the per-launch nonce, or a request with **no** `Origin` at all (non-browser clients).
- `/ws/agent` and `/ws/browser` are intentionally ungated, because the browser-control REST surface is deliberately open to any origin — gating the socket alone would be theatre.
- Name the residual out loud: any localhost-served page and any non-browser LAN caller qualifies; `--token` is what addresses that.

Then correct `reviews/1.12.9-tier1-v1.12.6-to-v1.12.8.md:7` to record B3 as **partially reverted**, not FIXED.

**Re-review scope:** Tier 0 only for the doc edit.

### B2 — npm dist-tags `beta` and `rc` still point at pre-guard releases, so `bunx haltija@beta` installs a server that clobbers the user's global `hj`
**(cross-cutting; outside-the-repo state)** — verified, both halves reproduced against the published tarballs.

Live: `npm view haltija dist-tags` → `{ beta: '1.3.0-beta.12', rc: '1.12.0-rc.5', latest: '1.12.8' }`. `latest` is post-fix, so the default path is clean; the exposure is confined to explicit `@beta` / `@rc`.

**(a) `@beta` clobbers `~/.local/bin/hj`.** The published `1.3.0-beta.12` was run under a synthetic `HOME` containing a *symlinked* `hj`: `[hj] Installed: …/.local/bin/hj` — the symlink was unlinked and replaced. That build keys on `Bun.file(source).size !== Bun.file(hjTarget).size` (the exact "install if the bytes differ" rule `CLAUDE.md` documents as the last-writer-wins bug), has no symlink protection, no version comparison, and **no `HALTIJA_NO_INSTALL` opt-out** (zero hits in the published tree). It has zero hits for `GUARDS_VERSION`/`retireLegacyServers`, i.e. it is precisely the pre-1.4.0 class `retireLegacyServers()` was built to stop — and `CLAUDE.md` names this scenario verbatim ("a stale `bunx haltija@beta` ends up owning the `hj` of an unrelated, up-to-date project"). Retirement stops the *process*; it cannot un-write the binary already on PATH.

**(b) `@rc` serves a network-reachable RCE.** Published `1.12.0-rc.5`, run isolated, given a CORS-*simple* POST (`Content-Type: text/plain`, no preflight) with `Origin: https://evil.example`: `POST /terminal/command {"command":"whoami; echo PWNED-MARKER"}` → **HTTP 200**, body `tonioloewald\nPWNED-MARKER`. That build routes to `spawn("sh", ["-c", …])`, sends `Access-Control-Allow-Origin: *` + `Access-Control-Allow-Private-Network: true`, and has zero occurrences of `isRefusedMachineControlPath`. HEAD refuses it (`f1046d3`, `src/machine-control.ts` prefix default-deny, wired in at `src/server.ts:1073`).

**Why blocker:** the fixes are already published (1.12.7/1.12.8) — only the pointers are stale. Two commands, no rebuild, no tests. The repo's own standard ("never ship around a bug whose fix is already written") applies at full strength.

**Fix at publish time:**
```
npm dist-tag add haltija@1.12.9 rc
npm dist-tag add haltija@1.12.9 beta     # or: npm dist-tag rm haltija beta
```
Retagging does **not** stop `npm i haltija@1.12.0-rc.5` from resolving, so a complete remedy also `npm deprecate`s the `1.12.0-rc.*` line and the pre-1.4.0 betas. See M4 — the same decision covers 1.12.7/1.12.8.

**Re-review scope:** Tier 0 only — re-run `npm view haltija dist-tags` after publish.

## Majors — decide before publish (fix, or record an explicit keep-decision)

### M1 — The `/ws/terminal` nonce gate refuses the desktop app's own agent-status socket, silently killing live status and shell updates
**`apps/desktop/renderer/agent-status.js:18`** — **verified**, including a live Electron measurement of the renderer's `Origin`.

`connectAgentStatusWs()` opens `ws://localhost:${window.haltija?.port || 8700}/ws/terminal` with **no nonce**, from a `loadFile()` renderer whose measured origin is `file://` (probed with this repo's own Electron binary — not the literal string `null`, not absent). `mayOpenMachineSocket` therefore takes the opaque-origin branch and requires a nonce match → 403. The release's own live test asserts exactly this (`src/ws-origin-live.test.ts:69`).

No configuration lets it connect: builtin server mints a nonce the client never sends; adopted external 8700 has no nonce at all, so `if (!opts.expectedNonce) return false` fails closed. `onerror` is empty and `onclose` schedules `setTimeout(connectAgentStatusWs, 3000)` — a silent forever-loop, with the server emitting a `refused /ws/terminal upgrade` warn every 3s.

Two things the finding overstated, corrected: the status bar is **frozen at launch state**, not hidden (`initAgentStatusBar` seeds it from `machineFetch('/terminal/status')` and `GET /agents`). What is lost is every *live* update — status-line changes, shell-joined/left/renamed — and terminal shells, which arrive only over the WS, never appear.

Secondary defect on the same line, independently confirmed: `window.haltija.port` **does not exist** — preload exposes only `internalPort`, `serverUrl`, `isPrivate`. This socket has always hardcoded 8700 regardless of the instance's real port. The sibling frame `apps/desktop/renderer/tabs.js:237-250` carries a comment diagnosing this exact defect *by name* and was converted; `agent-status.js` has the identical two defects and was skipped — the third repetition of the pattern `machine-relay.js:103` names.

**Not a blocker:** the standalone desktop app is `CLAUDE.md`'s deployment path 3, explicitly deprioritized. But "no known bugs at release" argues for the one-line fix.

**Fix:** `await window.haltija.wsNonce()` and append `?nonce=…`; derive the port from `window.haltija.serverUrl`. Then extend `src/desktop-spawn-wiring.test.ts` with a grep-shaped assertion that **every** `/ws/terminal` client under `apps/desktop/` carries a nonce — the current wiring test enumerates the `terminal.html` hop only, which is why it stayed green.
**Re-review scope:** correctness + blast-radius over the remediation diff only.

### M2 — The #42 guard set grew to nine methods, but its only user-facing documentation still describes five — and the module's shipped usage example now throws
**`src/test.ts:1-21`, `CHANGELOG.md:38`** — **verified**, reproduced against the built artifact.

`grep -c refuseMutationOnSharedDefault src/test.ts` → 10 (1 def + 9 sites: `click`, `type`, `press`, `focus`, `blur`, `navigate`, `refresh`, `runFile`, `suite`). `CHANGELOG.md:38` still reads "Mutating calls (`navigate`, `click`, `type`, `press`, `refresh`) now **throw**" — five of nine. `CLAUDE.md:501` is worse (three of nine), though it is not in `files`; `CHANGELOG.md` is.

`dist/test.d.ts` lines 1-21 are the `src/test.ts` header verbatim, and `package.json` exports `./test` → those types, so it is the hover text every consumer sees. There is no other `haltija/test` usage example anywhere in `README.md` or `docs/`. Running the documented snippet against the built artifact with no env vars set: `navigate`, `type`, `click`, `suite`, `runFile`, `focus`, `blur` **all throw**. A consumer whose CI does `bunx haltija --headless` (which binds 8700, in a *different* process, so the test process sees no env var) reads the five-method list, sees their call site absent, upgrades, and hard-fails.

Severity is major, not blocker: the failure is the safety property *working* — a loud throw naming its own remedy. Nothing is silently wrong. But the changelog costs adopters their advance warning, and the previous review already named this exact enumeration as compounding B1: the code was fixed, the claim was not.

**Fix:** make the module header show a targeted client (`createTestClient(process.env.HALTIJA_URL)` or an explicit `HALTIJA_PORT`, or `bunx haltija --private --headless`) and name the boundary in one line. In `CHANGELOG.md:38`, replace the list with the **rule** — "every call that changes the page or runs a fixture, including `runFile`/`suite`, the documented entry point" — since enumeration is what let the guard set fall behind in the first place.
**Re-review scope:** Tier 0 only.

### M3 — The #42 refusal message (and CHANGELOG) advertise `eval` as a read-only escape hatch, but `hj.eval` runs arbitrary JS in the shared browser's focused tab **(unverified)**
**`src/test.ts:171`, `CHANGELOG.md:38`** — reported by the correctness lens, not adversarially verified. I spot-checked both mechanical facts during triage and both hold: `HaltijaTestClient.eval` (`src/test.ts:315`) has **no** `refuseMutationOnSharedDefault` call, and `sharedMutationRefusal` ends with "Read-only calls (status, query, **eval**) still work against the default."

The failure path: a user or agent hits the new refusal on `navigate`/`runFile`, follows the message's own advice, and calls `hj.eval('location.href="/dashboard"')`. That is the #42 harm delivered through the remedy the guard recommends — and `eval` is the one method that subsumes every guarded method. Sanity-check this before acting, then either guard `eval` (it is a mutation vector by construction) or stop naming it as safe in both the message and `CHANGELOG.md:38`.

### M4 — 1.12.7/1.12.8 remain undeprecated on npm and the keep-decision the previous review required was never recorded **(unverified)**
**(cross-cutting)** — reported by the blast-radius lens. I confirmed the two mechanical facts: `npm view haltija@1.12.8 deprecated` is empty, and `grep -in 'deprecat|dist-tag' TODO.md AGENTS.md` returns nothing about npm.

The previous review's accepted follow-up (`reviews/1.12.9-tier1-remediation-v1.12.8-to-v1.12.9.md:114`) was "record the npm deprecation decision for 1.12.7/1.12.8 as a release step with an owner, **whichever way it goes**." Neither the action nor a decision against it exists. Those tarballs ship `terminal.html` loading rolling `cdn.babylonjs.com/babylon.js` into an unsandboxed frame holding a relay to `spawn('sh','-c')`. Publishing 1.12.9 fixes `^1.12.0` resolvers and does nothing for pinned lockfiles. Silence is the one outcome the previous review ruled out — decide it this release, either way, in writing.
