## Fix before the tag (verified majors; fix in beta.6, ahead of the 1.13.0 minor)

- [ ] **The #815 remote gate logs nothing on the server when it refuses a non-loopback peer.** (blast-radius, verified) `src/server.ts:4414`
  - **Failure:** haltija runs in a container, VM or WSL2 (NAT), or serves a phone or headset, and the host browser connects through a forwarded port. The peer address is the bridge or gateway, not loopback. Every `/ws/browser` upgrade gets a 403, and a browser cannot read why a WebSocket handshake failed. The widget retries forever and the server terminal stays silent. The machine-socket refusal a few lines below *does* `console.warn`, so this gate breaks a pattern the same function already follows.
  - **Fix:** on refusal, print one stderr line per distinct peer address (deduped, e.g. via `shouldEmitWarning`) naming the address and the `--token` / `HALTIJA_TOKEN` remedy. Add one sentence to the README, the CHANGELOG and `docs/CI-INTEGRATION.md` saying that port-forwarded containers and VMs count as other machines.
  - **Check that clears it:** extend `src/remote-gate-live.test.ts`. Open a WS upgrade to `/ws/browser` from the LAN address, capture the server's stderr, and assert it contains the peer address and `--token`. Assert that a second refusal from the same peer adds no new line. The test must fail with the warn line reverted.
